Look inside Windows memory,
WinDbg-style.

wineye inspects kernel crash dumps, raw memory images and live Hyper-V VMs from their memory alone — no debug transport in the guest. One Python file on MemProcFS's vmm.dll: no WSL, no pip package.

What it does

Passive, read-only analysis: the target does not know it is being looked at.

Any memory source

Kernel .dmp, .raw / .mem / .vmem images, any LeechCore device, or a live Hyper-V VM.

WinDbg commands

ps, lm, x, dq, dt, !vad, !handle, pattern search — with PDB symbols.

Crash-dump debugger

!analyze -v, stacks from kernel into user mode, .cxr / .trap, ~, u / uf, source lines and locals, .dump /u minidumps.

No MemProcFS for .dmp

A native engine reads every Windows x64 kernel dump format; own PDB reader, x64 unwinder and disassembler.

Server modes

Expose the target as an MCP server for AI agents, a gdbserver, or a DAP adapter for your IDE.

Scriptable

-c "ps;lm", --batch, --json, or import wineye and use the Vmm class.

Quick start

Windows x64, Python 3.10 or newer.

  1. Download wineye.py.
  2. For raw images, LeechCore devices and live VMs: get vmm.dll and leechcore.dll from a MemProcFS release (kernel .dmp files open without it).
  3. Open a dump:
python wineye.py --dump C:\dumps\MEMORY.DMP -c "!analyze -v"
python wineye.py --dump MEMORY.DMP --sympath C:\build\pdb -c "k;dv" --batch
python wineye.py --vmm C:\Tools\MemProcFS\vmm.dll --dump C:\dumps\MEMORY.DMP
python wineye.py --vmm C:\Tools\MemProcFS\vmm.dll --dump vm0.raw -c "ps;lm 4" --batch --json

Live Hyper-V VMs (--live, --vm N, --from-vm N) need administrator rights and the components set up by HvKdFusion.

Commands

Addresses are hexadecimal by default as in WinDbg (0x.. too, 0n for decimal), with registers, module!symbol, + and -.

CommandEffect
psprocesses
!process [pid]process details
.pid <n|-1>process context (-1 = physical memory)
lm [pid]modules
x <mod>!<sym>resolve a symbol through the PDB
db | dw | dd | dq <addr> [L<n>]hex dump
dt <mod>!<type> [field] [addr]type size, field offset and value
!vad [pid], !handle [pid]VADs, handles
s <addr> <len> <hex>byte pattern search
freeze, resume, r [reg...]control channel on a live VM (--vm N or .ctl N)

Debugger

On crash dumps, images and live VMs, with Microsoft's symbols (downloaded) or your private PDBs (--sympath).

CommandEffect
!analyze [-v]bugcheck, arguments, faulting context, instruction, module / driver, stack
k [n]call stack, kernel then user mode across the system call; source lines
~, ~<n>processors; switch to a processor
!thread, .thread <ethread>thread details and stack; switch to a thread
.cxr [addr], .trap <addr>, rcontext from a CONTEXT record / KTRAP_FRAME; registers
u [addr] [L<n>], uf <func>, lndisassembly (WinDbg syntax), whole function, nearest symbol
.frame [n], dvselect a frame; its parameters and locals (private PDB)
!process <pid> 7threads of a process with their stacks
.dump /u [pid] <file>user-mode minidump of a process, for WinDbg / Visual Studio

Server modes

Run --serve instead of the REPL. Read-only passive memory; the banner goes to stderr so stdout carries only the protocol.

ModeCommandUse
MCP--serve mcpJSON-RPC 2.0 over stdio for AI / agent clients: list_processes, list_modules, read_memory, resolve_symbol, stack, analyze, disassemble, ...
gdbserver--serve gdb [--listen 127.0.0.1:2159]GDB Remote Serial Protocol: target remote, then x/16xg, info registers
DAP--serve dap [--listen 127.0.0.1:4711]Debug Adapter Protocol for an IDE: modules, stackTrace, readMemory, evaluate

Limits

Passive memory gives no run control: no breakpoints, no single-stepping, no register writes. For that, use WinDbg/kd through HvKdFusion (hvkdfusion.py debug).
